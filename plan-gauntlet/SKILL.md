# Plan Gauntlet

기획 하나를 네 관문에 순서대로 통과시킨다. 관문마다 이미 설치된 스킬을 불러 쓰고, 단계 사이에서 멈춰 사용자의 결정을 받는다. 비판 결과가 앞 단계의 결론을 무너뜨리면 해당 단계로 되돌아간다.

입력: $ARGUMENTS

## 관문과 쓰는 스킬

| 단계 | 관문 | 불러 쓸 것 | 이 단계가 답하는 질문 |
|---|---|---|---|
| 0 | 입력 정리 | 없음 | 무엇을, 왜, 언제까지 정하는가 |
| 1 | 제1원리 | `meta-first-principles` 스킬 | 무엇이 사실이고 무엇이 관행·가정인가, 거기서 나오는 해법 후보는 무엇인가 |
| 2 | 스틸맨 | `steelman` 스킬 | 고른 방향보다 나은 대안이 있는가 |
| 3 | 프리모템 | `premortem-assassin` 스킬 | 이 계획은 안에서 어떻게 무너지는가 |
| 4 | 레드팀 | `~/.claude/skills/the-fool/references/red-team-adversarial.md` | 밖의 적은 이 계획을 어떻게 깨는가 |
| 5 | 정리 | 없음 | 무엇을 결정했고 무엇을 지켜볼 것인가 |

- 스킬은 Skill 도구에 이름을 넣어 부른다. 도구로 부를 수 없으면 `~/.claude/skills/<이름>/SKILL.md`를 읽고 따른다.
- 레드팀 단계에서는 `the-fool` 스킬을 부르지 않는다. 모드 선택 질문을 건너뛰려고 위 참고 문서를 직접 읽고 그 절차와 출력 양식을 쓴다. `the-fool`의 원칙(공격 전에 계획을 가장 강한 형태로 다시 쓰기, 가장 강한 3~5개만 제시, 비판으로 끝내지 않고 방어책까지 내기)은 따른다.
- 각 하위 스킬의 규칙(아첨 금지, 구체성, 출력 구조)은 그대로 지킨다. 분량만 아래 '출력 규칙'에 맞춰 줄인다.
- 역할을 나눈다. 프리모템은 내부 실패(일정, 의존성, 핵심 인물, 운영 부담, 성공의 역습)를, 레드팀은 외부 행위자(경쟁사, 악용하는 사용자, 규제기관, 악의적인 내부자, 공급망)를 맡는다. 3단계에서 다룬 위험은 4단계에서 되풀이하지 않는다.

## 0단계: 입력 정리

1. 인자를 해석한다.
   - 시작 단계: `제1원리`/`first`, `스틸맨`/`steelman`, `프리모템`/`premortem`, `레드팀`/`red`가 있으면 그 단계부터 시작한다. 없으면 1단계부터 시작한다.
   - 기획 내용: 파일 경로면 읽고, 텍스트면 그대로 쓴다. 없으면 대화 맥락에서 찾고, 그래도 없으면 묻는다.
   - 저장: `저장` 또는 `.md` 경로가 있으면 기획 문서를 파일로 쌓는다(아래 '기록'). 없으면 채팅으로만 진행한다.
2. 아래 세 가지를 확인한다. 빠진 것 중 결과를 바꾸는 것만 최대 3개 묻는다.
   - 기획 대상: 무엇을 하려는가(한 문장)
   - 성공 기준: 숫자와 날짜가 있는 결과. 없으면 프리모템이 "실패가 보이지 않는 계획"이라는 점부터 지적하게 된다고 알려 준다. 계획이 처음부터 여러 단계(예: 파일럿 → 본 출시, 이벤트 → 정식 기능)로 나뉘어 있으면 단계마다 따로 받는다.
   - 제약과 결정 기한: 예산, 인원, 마감, 되돌리기 어려워지는 시점
3. 중간 단계부터 시작하면 앞 단계가 만들었을 입력을 받는다. 스틸맨부터면 '고른 방향', 프리모템이나 레드팀부터면 '실행 계획'이 있어야 한다.
4. 작고 되돌리기 쉬운 결정이면 전체를 돌리지 않고 맞는 관문 하나만 권한다.

## 1~4단계 공통 진행

1. 해당 스킬을 불러 지금의 '기획 상태'를 입력으로 적용한다.
2. 결과를 '출력 규칙'에 맞춰 보여 준다.
3. 단계 끝에 AskUserQuestion으로 아래 표의 질문을 한다. 그 도구를 쓸 수 없으면 같은 선택지를 글로 묻는다.
4. 답에 따라 '기획 상태'를 고치고, 다음 단계로 가거나 '되돌아가기 규칙'을 따른다.
5. 다음 관문으로 넘어가기 전에 '단계별 성공 기준 점검'을 한다.

## 단계별 성공 기준 점검

관문을 거치며 계획이 여러 실행 단계로 나뉘는 일이 흔하다(예: 일정 문제로 "12월 이벤트 → 3월 본 기능"으로 쪼갬). 성공 기준이 원래 계획에만 걸려 있으면, 새로 생긴 단계는 판정 기준 없이 진행된다.

- 관문이 끝날 때마다 '실행 계획 요지'의 단계 수와 '성공 기준'의 단계 수를 맞춰 본다.
- 성공 기준이 없는 단계가 있으면 다음 관문으로 넘어가기 전에 그 단계의 목적에 맞는 기준(무엇을, 얼마나, 언제 판정)을 한두 개 제안하고 확인받는다. 단계의 목적이 원래 목표와 다르면(예: 본 기능은 체류 판정, 이벤트는 반응 확인) 그 단계 목적에 맞춘다.
- 사용자가 지금 정하지 않겠다고 하면 '남은 가정'과 결정 기록의 '다음 행동'에 "<단계> 판정 기준 정하기"를 기한과 함께 남긴다.

| 단계 | 끝에 묻는 것 | 선택지 |
|---|---|---|
| 1 제1원리 | 어느 방향으로 갈지 | 후보 A / 후보 B / (후보 C) / 다시 도출 |
| 2 스틸맨 | 원래 방향을 지킬지 | 진행 / 대안으로 재검토 / 더 조사 |
| 3 프리모템 | 치명타 3개를 어떻게 다룰지 | 계획 수정 후 진행 / 되돌아가기 / 위험 감수하고 진행 |
| 4 레드팀 | 공격 결과를 어떻게 다룰지 | 방어책 반영 후 정리 / 되돌아가기 / 위험 감수하고 정리 |

## 되돌아가기 규칙

3단계와 4단계의 비판 결과는 하나씩 아래 기준으로 분류하고, 분류에 맞는 행선지를 제안한다. 되돌아가기는 항상 사용자에게 확인받는다.

| 분류 | 판단 기준 | 가는 곳 |
|---|---|---|
| 방어 가능 | 감당할 만한 비용의 방어책이나 완화책이 있다 | 계획에 반영하고 다음 단계로 |
| 계획 수정 | 방향은 맞지만 실행 방법(순서, 범위, 일정, 담당)을 바꿔야 한다 | 계획을 고친 뒤 바뀐 부분만 3단계 프리모템으로 다시 점검 |
| 방향 붕괴 | 감당할 방어책이 없거나, 공격이 이 기획의 핵심 가치 자체를 무력화한다 | 2단계. 스틸맨에서 나온 대안을 후보로 다시 비교 |
| 전제 붕괴 | 1단계에서 '사실'로 둔 것이 틀렸거나 가정으로 드러났다 | 1단계. 틀린 사실만 고쳐 다시 도출 |

- 2단계에서 '대안으로 재검토'를 고르면 1단계로 돌아가 후보를 다시 고른다.
- 2단계에서 '더 조사'를 고르면 조사할 항목과 확인 방법을 적고 멈춘다. 조사 결과를 받으면 2단계부터 이어 간다.
- 되돌아갈 때는 영향을 받은 부분만 다시 돈다. 이미 통과한 결론 중 바뀌지 않은 것은 그대로 둔다.
- 되돌아가기가 두 번을 넘으면 분석을 더 돌리지 않는다. 결론을 내려면 무엇을 확인해야 하는지(데이터, 사람, 작은 실험)를 정리하고 멈추자고 제안한다.
- 되돌아간 이유와 바뀐 내용은 '기획 상태'의 수정 이력에 남긴다.

## 기획 상태

단계 사이에 아래 블록을 유지한다. 단계가 끝날 때마다 바뀐 줄만 갱신해서 보여 준다.

```markdown
## 기획 상태
- 대상: …
- 성공 기준: … (계획이 여러 단계면 단계마다: <단계>: 기준, 판정일)
- 제약·기한: …
- 확정 사실: … (1단계)
- 남은 가정: … (확인 방법 포함)
- 선택한 방향: … / 버린 대안: … (이유)
- 실행 계획 요지: …
- 열린 위험: … (나온 단계)
- 수정 이력: n단계 → m단계, 이유
```

## 출력 규칙

- 사용자의 언어로 답한다.
- 각 단계 맨 위에 `관문 n/4: <이름>`을 붙여 지금 위치를 알린다.
- 단계 하나의 결과는 한 화면 안팎으로 줄인다. 하위 스킬의 출력 양식은 따르되 표와 목록을 우선하고 서술은 줄인다.
- 결론을 먼저 쓰고 근거를 뒤에 쓴다.

## 5단계: 정리

마지막에 결정 기록 한 장을 만든다.

```markdown
# 결정 기록: <기획 이름>
- 결정: …
- 이유: … (어느 관문에서 확인됐는지)
- 버린 대안과 이유: …
- 남은 위험과 감수 이유: …
- 성공 기준: 실행 단계마다 기준과 판정일 (정하지 못한 단계는 "미정"으로 쓰고 다음 행동에 기한과 함께 남김)
- 조기 경보: 날짜가 있는 확인 항목 3~5개 (프리모템의 tripwire와 레드팀의 방어책에서)
- 다음 행동: 담당, 기한
- 수정 이력: …
```

저장하지 않고 진행했다면 정리 뒤에 파일이나 노션으로 남길지 한 번 묻는다.

## 기록

저장을 요청받았으면 지정한 마크다운 파일에 '기획 상태'와 단계별 결과 요약을 쌓는다. 경로 없이 `저장`만 받았으면 현재 작업 폴더의 `plans/<YYYY-MM-DD>-<기획-이름>.md`를 만든다. 단계가 끝날 때마다 파일을 갱신하고, 마지막에 결정 기록을 맨 위에 둔다.

## 하지 않는 것

- 사용자가 고르지 않은 방향으로 혼자 넘어가지 않는다.
- 되돌아가기를 확인받지 않고 실행하지 않는다.
- 하위 스킬의 원본 파일을 고치지 않는다.
