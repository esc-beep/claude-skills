# 보고서 종류별 구성

다섯 종류 중 하나를 고르고 아래 순서를 따른다. 섹션은 내용에 맞게 합치거나 빼도 된다. 다만 빈 섹션과 빈 탭은 두지 않는다. 대괄호 숫자는 `sources.md`의 출처 번호다.

## 모든 종류에 공통

- 첫 화면(머리)에 답 한 문장과 핵심 그림 또는 숫자 카드를 둔다. 장식용 hero는 두지 않는다. [1]
- 기준 시각(as-of)과 정본 위치를 머리에 둔다. [2]
- 제목에는 주제가 아니라 결론을 쓴다. 예: "Stage 이전 회고"보다 "Stage 이전: 자원은 옮겼고 연결이 빠졌다". [1]
- 섹션이 4개 이상이면 목차를 둔다. 원자료는 `<details>`로 접고, 근거와 출처는 끝에 보이게 둔다. [1][8]
- 끝은 "정할 것"(누가, 언제까지, 권장안)과 "확인하지 못한 것"(무엇을, 왜)으로 맺는다.
- 숫자 카드는 3~5개. 값, 단위, 기준(언제·어디서), 출처 종류를 붙인다. [3]

## 1. 회고·사고 분석

목적: 무슨 일이 있었고, 왜 그랬고, 다음에는 무엇을 바꾸는가.

1. **머리**: 제목(결론), 메타 pill(상태, 기간, 영향 범위, 담당 티켓), 요약 상자(원인 한 문장, 영향 수치, 복구 방법), 숫자 카드. [8]
2. **흐름**: 프로젝트 단계 Gantt 또는 사고 타임라인(`schedule.md`). 사고 타임라인은 세로 목록, 시각은 mono, 영향 시작·완화·복구를 모양이 다른 점으로 나눈다. 틀린 가설과 그로 인한 지연도 남긴다. [8]
3. **무엇이 일어났나**: 문제 목록. 10건이 넘으면 필터 표(시기, 유형, 상태, 검색)로 둔다(`interaction.md`).
4. **왜**: 원인 유형별 분류(정렬한 막대)와 근본 원인 사슬(상자와 화살표). 원인에서 대책으로 이어지는 대응 그림이 있으면 같은 줄에 나란히 둔다.
5. **찾아낸 방법**: 무엇이 잘 찾았나(막대나 작은 표).
6. **다음에 바꿀 것**: 대책, 완료 판정, 담당·기한(정해지지 않았으면 그렇게 쓴다). [8]
7. **남은 일, 정할 것, 확인하지 못한 것**.
8. **근거**: 티켓 표, 정본 노트, 작성 근거와 한계. [8]

## 2. 계획

목적: 무엇을 어떤 순서로 하고, 언제 무엇으로 판정하는가.

1. **머리**: 무엇을 어디서 바꾸는지 짧은 제목, 한 문장 요약, 요약 셀(공수, 범위, 새 자원 수, 위험 표시). [1][8]
2. **요청과 목표**: 요청 원문 또는 목표, 범위 안과 밖. [8]
3. **일정**: Gantt(단계, 병렬, 판정 시점 마일스톤)와 오늘 선. 판정 시점마다 무엇으로 판정하는지 쓴다(`schedule.md`). [7][2]
4. **흐름 그림**: 바뀌기 전과 뒤, 또는 실행 순서. 범례는 캡션에 둔다. [8]
5. **핵심 주장 2~5개**: 행동 기준으로 나누고(파일·레이어 기준이 아님), 주장마다 증거 하나와 근거 수준(읽음, 추론, 미확인)을 붙인다. [1]
6. **위험 표**: 위험, 가능성·영향, 완화, 담당. 알려진 약점도 쓴다. [2]
7. **롤아웃과 롤백**: 단계별 지표·임계값, 롤백 방법·예상 시간·검증. [2]
8. **결정할 것**: 만들 것이 달라지는 갈림만 2~5개, 권장안을 기본값으로. [1]

## 3. 상태 보고

목적: 지금 어디이고, 다음에 누가 무엇을 하는가.

1. **상태 배너**: 단계, 주 작업, 수치 1~2개, 다음 게이트, as-of. [2]
2. **다음 단계 띠**: 1~3개. "누가 → 무엇을 → 그러면 무엇이 풀리나"로 쓰고, 없으면 "없음" 한 줄. [2]
3. **숫자 카드**: 4개 안팎, 전 기간 대비 변화와 추이선. [8][3]
4. **성공 기준**: 기준마다 확인 방법과 상태 pill. 관심사별로 묶고 "범위 밖"을 붙인다. [2]
5. **작업 표**: id, 내용, 담당, 상태 pill, "X 다음". 의존 그래프는 그리지 않는다. [2]
6. **추이 그림**과 캡션, **이월 항목**(리뷰 중, 막힘, 밀림과 사유). [8]
7. **위험과 열린 질문**.

갱신 보고라면 HTML 끝에 상태 JSON 블록을 두고, 다음 갱신 때 비교해 바뀐 것만 머리에 적는다. 조회에 실패한 칸은 "오래됨"으로 표시한다. [2]

```html
<script type="application/json" id="report-state">{"asOf":"2026-11-03","items":{"T1":"done","T2":"open"}}</script>
```

JSON 안의 `<`는 `<`로 쓴다. [2]

## 4. 비교·판정

목적: 무엇을 고를지, 왜 그것인지.

1. **머리**: 첫 문장에 판정, 판정 chip(가능, 조건부, 불가), 판정한 사람과 기준일. [1]
2. **기준**: 판정 기준과 가중치(필수, 조건부, 권고).
3. **선택지별 차이 그림**: 같은 축척의 작은 그림을 나란히(small multiples). [1]
4. **장단점 표**: 상태 chip과 글자를 함께. 넓으면 첫 열 고정. [1]
5. **시나리오별 결과**: 같은 규칙 3~6개를 같은 순서로 놓고 통과·실패·건너뜀을 글자와 모양으로. 첫 갈림을 표시한다. [7]
6. **계산기**(값을 바꿔 보는 것이 판단을 돕는다면): 기본값은 현재 실측값(`interaction.md`). [1]
7. **권고와 이유, 남은 조건**.

## 5. 학습·설명

목적: 읽는 사람이 개념이나 변경을 이해하고 스스로 확인한다.

- 탭 없이 긴 한 페이지와 목차. [9]
- 순서: **배경 → 직관 → 본문 설명 → 확인 퀴즈**. [9]
  - 배경: 아는 사람은 건너뛸 수 있다고 표시한다. 바로 관련된 배경만 쓴다.
  - 직관: 장난감 데이터로 그린 그림 하나. 단계별 재생 그림이 잘 맞는다(`interaction.md`).
  - 본문 설명: 질문 → 단계별 메커니즘 → 경계 사례 → 기억할 것. 정의와 경계 사례는 callout으로. [1]
  - 코드나 설정을 보이면 틀리기 쉬운 곳 2개를 골라 짚는다. [8]
  - 퀴즈: 5문항 객관식, 중간 난이도, 함정 없음. 누르면 정답 여부와 선택지별 이유를 보인다. [9]
- 그림 종류는 적게 골라 되풀이한다. 단순화한 화면 그림과 예시 데이터가 든 흐름 그림이 좋다. [9]
- 발표 장표와 대본은 이 스킬 범위가 아니다.
